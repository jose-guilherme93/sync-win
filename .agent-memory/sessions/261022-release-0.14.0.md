## What shipped

created, as the workflow requires:

- Docker Hub `joseguilherme93/sync-win`: `0.14.0`, `v0.14.0`, `latest`
- GHCR `joseguilherme93/sync-win`: the same three, same digest

Both features landed in the same release because both are `feat:` commits
between `v0.13.2` and `main`: a release that ships both cannot describe only
one of them, which is why the notes for the notification work live in the same
section as the network work.

## The CI finding worth keeping

The browser end-to-end job failed three times in an afternoon with
`The operation was canceled`, always during `Install agent-browser and Chrome`,
always at about 10m18s in a job whose bound was 10 minutes. It was not the
test: `agent-browser install --with-deps` pulls apt packages, and
`fonts-noto-cjk` alone is 61 MB. On a congested mirror that took eight
minutes, and the job was cancelled before the suite ever started.

A green run on the same commit took 5m49s. Two runs of the same commit, one
green and one cancelled, is the signature of a resource bound, not a
regression.

- the job bound is 18 minutes now,
- the install step has its own 12-minute bound, so a stuck install fails on
  its own name.

## The lesson

A required check that fails on the runner's network is indistinguishable from a
broken change until the log is read. The log said `The operation was canceled`
inside the install step, with no test output at all: the first line of the
log is where that answer lives.
