## What was asked

The application log screen (Administration → Settings) had a "Live" toggle that
re-fetched page 0 every five seconds. That reset pagination and scroll position,
and it was the last item the app-logs session had explicitly left undone.

## What was built

Worktree `sync-win-log-sse`, branch `feat/log-sse`.

### Server

- **`GET /api/logs/stream-token`** (`POST`) issues a single-use, 30-second
  ticket. EventSource cannot send an `Authorization` header; the session cookie
  proves the identity and the ticket makes the long-lived GET deliberate. The
  same ticket store as the notification stream is reused.
- **`GET /api/logs/stream?ticket=...`** is `text/event-stream`. It accepts the
  same filters as `GET /api/logs` and writes `id: <id>` + `data: <entry>` for
  each new row. `after_id` (or `Last-Event-ID`) is the cursor; without one the
  stream starts at the owner's newest entry, so a page that already rendered
  history is not replayed. Idle streams get a keep-alive comment every ~15s.
- **`logging.Store.ChangesAfter` / `LatestID`** walk `id`, which is monotonic.
  Ordering by `ts` would skip entries whose timestamp is older than one already
  sent (the logger batches and timestamps at enqueue time).
- **The server tails the table** on `logStreamInterval` (1s; shortened in
  tests) instead of publishing from the logger. That keeps every filter in one
  SQL builder, which is what the page already uses; a publisher would have to
  duplicate level/category/search/from/to matching and owner resolution. The
  logger flushes every 5s, so this is the same latency the client poll had,
  without the client poll.
- `handleLogs` now shares `logParamsFromRequest` with the stream so the two
  cannot drift.

### Web

- `AppSettings.svelte` opens the stream when "Live" is on, prepends each entry
  (deduplicating by id), increments the total, and refreshes the stats card on a
  1.5s debounce. Turning live off closes it; changing a filter tears it down and
  reopens with the new query.
- The ticket is single use, so `onerror` closes the EventSource (whose automatic
  reconnect would reuse the dead ticket) and reconnects with a fresh ticket and
  exponential backoff, capped at 30s. The reconnect state is shown next to the
  toggle instead of failing silently.
- `onDestroy` closes the stream and clears the retry/stats/search timers.

## Verification

- Server: `go build`, `go vet`, `go test ./...` green; `golangci-lint v2.14.0`
  with `--new-from-rev=bb91b03` reports 0 issues (one `cancelled` misspelling
  fixed).
- New tests: ticket required/single-use, token requires a session, pushes a new
  entry with SSE framing, does not replay history, applies the level filter.
- Web: 20 files / **155 tests** (was 152), `svelte-check` 0 errors, `vite build`
  clean. New tests cover streaming a new entry, reconnecting with the new filter,
  and closing the stream when live is turned off.

## Not done

- The stream still has ~5s worst-case latency because the logger batches writes
  on a 5s flush. Lowering `FlushInterval` would shorten it but changes the write
  profile for every log line, so it was left alone.
- Only the application log screen uses the stream. Device journal logs
  (`/api/devices/{id}/logs`) are still fetched per page.
- The reconnect backoff lives in the component; a second consumer would need the
  same logic. It is ~20 lines and was not extracted.
