# Security

This document describes the security model, rules, and best practices for Linux Environment Manager.

## Principles

1. **Agent-first architecture**: the agent is the only component allowed to touch the local machine. The server never executes arbitrary commands on clients.
2. **Least privilege**: only explicitly allowed files are collected. Sensitive data is excluded by default.
3. **Defense in depth**: multiple layers of validation, encryption, and access control.
4. **No secrets in plaintext**: passwords, tokens, and credentials are always hashed or encrypted.
5. **Explicit contracts**: everything the agent collects and executes is defined in a written contract.

## Authentication

### User accounts

- Users register with email and password.
- Passwords are stored as salted SHA-256 digests: `s256$salt$hash`.
- Sessions are managed via random Bearer tokens stored server-side with 30-day TTL.
- The `GET /api/auth/me` endpoint validates the current session.
- All API endpoints (except `/health`, `/api/auth/*`, `/install/*`) require a valid Bearer token.

### Device tokens

- Each device gets a unique random token at enrollment time.
- The device token is used for all agent-to-server communication.
- Device tokens are never shown in the UI or written to server logs.
- The `Authorization: Bearer <device_token>` header authenticates agent requests.

### Enrollment tokens

- Single-use tokens with 15-minute expiry.
- Generated by the dashboard and embedded in the install script.
- Consumed during `POST /api/agent/enroll` to create the device.
- Bound to the owner who generated them.

## Data protection

### Passwords

- Stored as salted SHA-256 digests: `s256$salt$hash`.
- Never transmitted in plaintext over the network (use HTTPS in production).
- Never logged or stored in plaintext.

### Notification provider credentials

- Encrypted with AES-GCM before storage.
- The frontend never receives raw secret values.
- `PublicFields()` on each provider declares which fields are safe to expose.
- Only the encrypted blob is stored in the database.

### Preference files

- Only explicitly allowed files are collected (allowlist-based).
- Sensitive files are excluded by default:
  - `id_rsa*`, `id_dsa*`, `id_ecdsa*`, `id_ed25519*`
  - `*.pem`, `*.key`, `*.p12`, `*.pfx`
  - KWallet, browser credentials, tokens, keys
- Content is scanned for known secret patterns:
  - PEM private keys
  - AWS access key IDs (`AKIA...`)
  - GitHub tokens (`ghp_`, `gho_`)
  - Slack tokens (`xox*-`)
  - Stripe live keys (`sk_live_`)
  - Google API keys (`AIza...`)
- Binary files are rejected for non-saves categories.
- Files with null bytes (binary content) are rejected.
- Empty files are rejected.
- Base64-encoded saves bypass secret scanning (content cannot be inspected).

### File size limits

- Text files: 256 KiB (server) / 512 KiB (agent, before upload).
- Save-game files: 1 MiB per file, 16 MiB per sync cycle.
- HTTP request bodies: 2 MiB maximum.

### Storage

- SQLite with WAL journal mode and foreign keys enabled.
- Preference file contents are mirrored to `/data/<device>/<category>/` for easy inspection.
- SQLite remains the source of truth.
- Database migrations are embedded in the server binary and applied idempotently.

## Network security

### HTTPS

- Use HTTPS in production. The server does not enforce TLS by default.
- Place a reverse proxy (nginx, Caddy, Traefik) in front of the server for TLS termination.

### CORS

- The production dashboard is served from the same origin as the API (no CORS issues).
- For development, CORS headers are configured for the Vite dev server.

### Rate limiting

- Request bodies are capped at 2 MiB.
- Enrollment tokens are single-use with 15-minute expiry.
- Notification events are throttled: 15-minute window per `(event_type, device_id)`.

## Agent security

### Local policy

- The agent enforces local policy via `~/.config/lem/policy.json`.
- Any command type can be disabled locally.
- Disabled commands are reported back to the server with a reason.
- The server never forces execution of disabled commands.

### Command execution

- All commands run with hard timeouts (default: 900 seconds).
- Output is capped at 64 KB.
- Docker exec commands have a 30-second timeout.
- Package names are validated against a restricted charset.
- Path traversal (`../`) is rejected.

### File collection

- Only files in the explicit allowlist are collected.
- The agent never scans broad parts of the home directory.
- Content hashes prevent re-uploading unchanged files.
- Individual file errors are logged and skipped; they never abort the batch.

### Docker management

- Container IDs are validated against injection (`validContainerID()`).
- Compose file writes are restricted to valid compose filenames.
- All Docker operations check `DockerIsAvailable()` before execution.
- All Docker actions are logged in the audit trail.

## Server security

### Input validation

- All uploaded files are validated for size, encoding, content, and path.
- Filenames are checked against a restricted charset.
- Categories are validated against a fixed set.
- Relative paths must not contain `..` (path traversal).

### Secret redaction

- The structured JSON logger automatically redacts secrets before storage.
- Known patterns (API keys, tokens, passwords) are replaced with `[REDACTED]`.
- Redacted entries are marked in the database.

### Audit trail

- All Docker commands, authentication events, and notification events are logged.
- Logs are append-only and never modified.
- The audit log is queryable via the API.

## Deployment security

### Docker

- The server runs as a non-root user inside the container.
- The `/data` volume is mounted for persistence.
- Use `network: host` only if the server needs to be reachable on the host network.

### Agent installer

- The installer verifies the agent binary via SHA-256 checksum.
- The installer creates a dedicated user and group.
- The systemd service is hardened with `Restart=always`, `RestartSec=15`, `StartLimitIntervalSec=0`.
- The installer verifies the connection to the server before declaring success.

### Systemd hardening

```ini
[Service]
ExecStart=/home/user/.local/bin/lem-agent daemon --server http://SERVER:8080
Restart=always
RestartSec=15
StartLimitIntervalSec=0
```

## What is NOT stored

The server never stores:

- passwords or password hashes (only salted SHA-256 digests)
- private keys or certificates
- browser credentials or cookies
- KWallet data
- SSH keys
- API tokens or secrets (except encrypted notification provider configs)
- full home directories
- large binary files (except base64-encoded saves up to 1 MiB)

## Reporting security issues

If you discover a security issue, please report it responsibly. Do not open a public GitHub issue for security vulnerabilities.
